# UBS Gold 7戦略比較 決定履歴

## 2026-09-02: 比較開始時の方針

### 背景

`Sets_v6_faithful14/Sets_v6_faithful14/`にある14 setを確認した結果、実設定値`ForceSymbol=XAUUSD`のsetは7個だった。利用者は、この7戦略を実運用に近い条件で比較し、後から総合報告書へまとめることを希望している。

### 決定

- 最初に互換性、正しいTester時間足、資金管理設定を確定する。
- 原setは変更せず、SHA-256と主要入力値を基準情報として保存する。
- 原set忠実比較と同一リスク比較を分ける。
- 短期スモークテスト後に、既存WF1～WF4相当期間の28件へ進む。
- 生データと段階別集計を`data/ubs_strategy_comparison/`へ保存する。
- 最終報告書と画像は`doc/reports/`へ保存する。

### 理由

- フォルダ名はv6系だが、2026-09-02時点のUBSデモ版はv7.5であり、パラメータ互換性を先に確認する必要がある。
- 7 setの`LotPerBalance_step`、`HistoricalMaxDD`、`MaxTrades`などが同一ではなく、原設定の利益額だけでは戦略能力とリスク量を分離できない。
- 一部setはファイル名からTester時間足を特定できず、内部設定`ST1_Timeframe`をTester時間足と断定できない。
- 段階別の成果物を残すことで、最終報告書の数値と判断を再検証できる。

### 影響

- 正しいTester時間足または互換性を確定できないsetは、本試験を開始しない。
- 資金管理を変更する場合は原setを複製した派生setだけを使用する。
- 今後、期間、モデル、リスク正規化、ストレス値などを変更する場合は、この文書へ変更理由と影響を追記してから実装・実行する。

## 2026-09-02: v7.5既定値表現の訂正と実効入力固定

### 訂正理由

旧setに存在しない入力は、スモークレポート上で5戦略すべて同じ値だった。しかし、これだけではEAバイナリのコンパイル済みデフォルト値と、Strategy Testerに保存されていた値を区別できない。このため「v7.5の既定値で補われた」という表現は根拠に対して断定的だった。

### 決定

- 正式な表現を「v7.5／Tester側の基準値で補われた」へ訂正する。
- `ExpertParameters`を指定しないデフォルト対照テストを、スモークと同じ市場・期間・モデル・資金条件で実行する。
- 対照レポートの入力値と、旧setで補われた入力値を比較する。
- 7戦略それぞれのスモークレポートに記録された実効入力から、v7.5用の完全な派生setを作成する。
- 派生setは原setと別の`data/ubs_strategy_comparison/derived_sets/`へ保存し、原setを変更しない。
- 派生setを再読込し、レポートの全入力が作成元スモークと一致することを確認してからPhase 2へ進む。

## 2026-09-02: Phase 2実ティックpreflightデータ品質ゲート

### 位置づけ

MT5の`history ticks synchronized`情報は、ローカルTesterエージェントが起動して履歴を同期した後にログへ出力される。したがって、MT5起動前の静的検査だけでは同期範囲を保証できない。

Phase 2では、最初のウォームアップまたは基準runを実行した直後にTesterログを検査し、PASSした場合だけ後続比較へ進む。この実行後検査を、後続ケースに対するpreflightデータ品質ゲートとして扱う。

### PASS条件

- Testerログ内で、対象Symbol、Period、FromDate、ToDateに一致する最新テスト区間を一意に取得できる。
- 同区間に`history ticks synchronized from ... to ...`が存在する。
- 同期開始日はFromDate以前である。
- 同期終了日はToDate直前の最終平日以後である。
- 同区間に`real ticks absent`、`no real ticks within a day`、`every tick generation used`のいずれも存在しない。

### 判定結果の保存

同期開始日・終了日、要求終了日、欠損警告、判定理由、抽出元ログをJSONへ保存する。累積Testerログでは、対象条件に一致する最後の完了テスト区間だけを評価する。

### 影響

ゲートがFAILした場合、当該ウォームアップ結果は診断証拠として保持するが、性能比較の基準には採用せず、後続ケースを開始しない。履歴同期後に新しいrun IDで再実行する。

### 実装・実ログ検証結果

- 保存済み累積Testerログから対象条件の最新完了区間を抽出する共通パーサーを実装した。
- UBSランナーはmodel=4の各実行後に`tick_data_quality.json`を保存し、FAIL時は後続戦略を停止する。
- 保存済みrunを監査する`audit-ubs-tick-data`コマンドを追加した。元のrun manifestは変更せず、別の`tick_data_quality_summary.json`へ保存する。
- 同期不足run `20260902T130931213191_640f76c3`は、`xau_sr_scalp_h1`で同期終了`2026.08.27`、要求日`2026.08.28`、生成ティック警告4件となりFAILした。
- 正式基準run `20260902T143126585336_b4e7cdd1`は、7戦略すべて同期終了`2026.08.28`、要求日`2026.08.28`、生成ティック警告0件となりPASSした。

### Phase 2比較ランナーの共有方針

四半期別28ケースでは、既存のMT5実行、setステージング、HTML入力・成績・deal解析、ログ保存、UBS入力互換性比較を再利用する。Phase 1で確定した忠実拡張set manifest、最終再現検証PASS、正式基準runのティック品質PASSを開始条件とし、重複する専用処理を新設しない。
