# ログ重複整理の小規模保存・復元試験

## 目的・変更理由（実装前の記録）

2026-09-27。読み取り調査でログ957件・7,092,684,149 bytesのうち、
累積ログの先頭一致による重複6,892,429,554 bytesを確認した。
各テストは累積ログを保存し、既存の再監査はそのログ内の最後の一致ブロックを読む。
最新ログへの単純な参照置換では別テストを監査する危険がある。
元パス・長さ・SHA-256を記録し、元のバイト列を復元できる方法を試す。

## 範囲と計画

1. 独立した保存・復元モジュールを追加する。既存テスト実行・監査処理は変更しない。
2. 同名ログの先頭一致をハッシュで判定し、共通本体をgzipで保存する。
3. 元パス（data相対）・長さ・SHA-256・本体参照をmanifestに記録する。
4. 新規の試験専用フォルダへ復元し、全件の長さとSHA-256を照合する。
5. 既存の audit_latest_real_tick_test を再利用し、原本と復元ログの監査結果を比較する。
   比較から除くのは保存先変更による source_log のみ。監査行番号も比較する。
6. パストラバーサル・破損・空ファイル・非包含ログ・既存出力保護を単体テストする。
7. 実データは2026-09-10の連続した3ケースのTesterログに限定する。
   結果と計測値をdata/log_archive_pilot内に残す。Pythonはuv管理、直列実行。

原本の削除・置換、manifest書換え、全件処理、MT5起動、commit/pushは行わない。
gzipは低圧縮レベルを用いて負荷を抑える。試験で容量は一時的に増加する。
失敗時も原本を保護し、途中成果物は削除せず原因調査に残す。

### 旧形式1件の追加確認と判定

初回の自動検証は旧形式1件の `max_fallback_ratio` 欠落により `status=fail`。
この結果を上書きせず `verification_result.json` に保持した。
対象は `model_comparison_1y/20260902T162029093739_4e2ec09f/08_real_ticks_xau_sr_scalp_h1_interrupted_20260902T171033109976`。

原因は保存済み監査JSONに現形式の5項目がないこと。原本や復元の破損ではない。
追加確認では既存監査関数の既定値0（生成ティック許容なし、厳格側）を用いて
原本と復元を再監査した。source_log以外の現形式全項目が一致し、保存済みJSONに
存在する全項目も一致した。124921～127556行の同じテストを読んでいる。
当時の `passed=false` と `generated_tick_fallback_detected` も維持された。
保存・復元の成功と、元のバックテスト品質の合否は区別する。
追加照合の結果を `legacy_audit_supplement.json` に別記した。

したがって、全ログの内容復元は確認済みであり、再監査は370件の自動一致＋1件の
旧形式追加確認で一致。ただし初回の自動結果単体をPASSとは扱わない。
